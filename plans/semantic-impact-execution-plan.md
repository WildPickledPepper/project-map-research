## 1. 目标与使用方式

工具面向多语言、跨进程、强交互、数据密集型的桌面/Web 应用。让 AI 在定位 issue、提出修改、检查 diff 和验证结果时，查到有关模块之间的连接、数据含义、共享状态、适用条件和运行证据，识别“改动 A 会影响哪些 B，以及还要验证什么”。

保留项目地图、代码/接口/数据图和运行视图，在它们之上组织任务上下文。全项目覆盖与查询精度分别管理：所有实际模块和边界进入账本；复杂别名和值流按所需能力调用原生分析器，返回已证明关系、条件候选和具体缺口。

| AI 当前任务 | 默认给出的内容 | 继续展开的入口 |
|---|---|---|
| 初次理解项目 | 模块职责及依据、语言、入口、运行模式、构建产物、模块间主要连接 | 模块→接口→符号→源码；覆盖与缺口 |
| 根据 issue 定位 | 现象、预期、触发配置；相关入口、提供者、消费者、状态与资源路径 | 精确搜索、正反向追踪、源码、适用运行记录 |
| 检查修改方案/diff | 前后变化、受影响依赖方、条件和副作用、现行前提、需验证的问题 | 每项变化的源码依据、关联对象、测试入口和未解析关系 |
| 运行与验证 | 实际分支、请求/对象身份、状态变化、资源指标、断言结果 | 同版本静态路径、失败/恢复记录、尚未运行的场景 |

期望行为来自 issue 表述、现有测试和有依据的源码前提。自动提取的事实与 AI 提出的风险假设分别标记；推断出的业务含义需要核验。历史 PR 的答案不进入工具输入。

## 2. 保留的成果与必须补的缺口

已有自动发现、多语言事实、统一图、SQLite 查询、版本隔离、更新/失败恢复、CLI/MCP 和限定场景运行采集继续使用。原生补充已恢复实际编译上下文中的头文件事实，并接入部分 Rust MIR/值流，详见[交付记录](../experiments/2026-10-26-r0-r1/reuse-followup.md)。

当前主要缺口如下：

1. **原生成本与身份**：真实 C++ 的完整 SVF 运行超过 13 GiB；CLI/Python 存在重复求解和未验证的 points-to 身份对应；Rust Linux Debug 的 SVF 补图尚缺。统一图目前不导入未验证的 points-to 边。
2. **全模块关系验收**：129 组件的代表性事实检查已通过，全部调用/数据语义尚未按 G02 完成核查；边界、数据和运行的完整分母继续保留。
3. **修改影响表达**：当前 `impact` 主要是反向遍历，需要把变更前后身份、条件、读写、触发依赖、副作用与验证入口组织成可消费的任务结果。
4. **效果证据**：局部链路、节点数量和旧 AI 试用不能回答当前工具是否提高修复正确率；需要后续冻结的对照实验。

依据：[AI 上下文需求](../research/ai-context-requirements-2026-10-26.md)、[全部 24+7 条材料分析](../research/regression-context-gaps-2026-10-26.md)、[原生预算调查](../research/native-analysis-budget-2026-10-26.md)。三份研究分别记录论文结论、源码检查和待测方案，本计划中的改进尚未实测。

## 4. 分阶段执行、交付与验收

沿用 R/G 编号。每个工作批次主动分析/实现最多 90 分钟、墙钟最多 120 分钟，同一局部链最多 30 分钟。下列批次数是本轮投入上限；到限提交收据并停止该阶段的新实现，逐项报告通过、失败和剩余项。必需项未通过时，相应 G 门槛保持未通过，独立阶段可以继续。

### 4.1 R0/R1：定位成本并整理原生结果路径（1 批）

**输入与操作**：复用已有 411 个编译单元生成并完成 LLVM O1 的 C++ bitcode；读取实际执行版本的帮助/API，核对 PySVF `1.0.0.50` 与已下载源码接口的差异。先在小型独立题上验证阶段控制和导出，再按诊断需要执行有上限的真实输入。

- 分别记录加载/建 PAG、Andersen、MemorySSA/SVFG、导出阶段的耗时和资源；接口无法分阶段时，记录能观察到的粒度与缺失项。
- 对照 PTA 与 SVFG 的能力和成本；仅别名结果按别名能力记账，既有六项值流题继续用值流标准验收。
- 确定同进程导出或固定版本兼容的结果复用入口，验证节点身份。已发生崩溃的 `-read-ander` 路径须先有明确修复依据和独立复现结果才可采用。
- 原生补充沿用当前快照来源；Python 导出重新求解的成本独立列出，避免将顺序求解误计为峰值翻倍。

**交付**：阶段资源表、准确命令/版本/输入配置、单次求解导出接口决定、points-to 身份检查结果、首次失败及重试依据。

**验收**：能够据实区分已测成本与未知阶段；选定路径在独立题中保持原生对象身份及预期正负例。真实分析继续超预算时，发布失败结果并转入下一批的路线决定。

**停止条件**：真实输入每次原生分析最多 600 秒、进程树内存上限沿用 13 GiB；最多一次有修复假设的复验。重编全部 C++、提高内存上限和同时运行多个重型分析均不进入本批。

### 4.2 R0/R1：确定可用的效果复用路线并清理剩余原生缺口（1 批）

**执行顺序**：

1. 根据前一批结果选一条原生路线。若主要成本在完整 SVFG，验证上游可提供的必要图/效果形式；若 Andersen 前置已经超预算，SVF DDA 仍有该前置，直接检查可组合候选的适用性。
2. 先核查实际可导出内容：参数/返回、读写对象与字段、全局/共享状态、回调、条件、外部副作用及配置。摘要需能由原生引擎跨函数组合和处理递归。
3. 现有入口不能提供时，最多给 Infer 一个 45 分钟的准入窗口，核查编译兼容、所需结构化结果和组合能力。只输出告警或不可访问摘要时，按能力不满足退出；不因此继续引入 CodeQL/CTU 等第二批新候选。
4. 利用已有 Rust 捕获补 Linux Debug；按同一身份域核对其它已捕获配置。独立失败单列，不扩大为重跑全部平台。

**交付**：逐事实能力/来源表、一条已验证的导出路线或明确拒绝决定、Rust 配置清单、所影响模块和查询的 required gaps。语言基础导航继续使用已准入提供方。

**验收**：既有六项值流题及跨文件/不同布局组合检查通过，涵盖参数/返回、字段写读、复制与借用、独立实例、共享状态和回调；区分候选与确定关系。缺外部摘要时保留未知副作用。同精度比较成本和误连/漏报。

**停止条件**：本批结束必须形成采用/拒绝决定。无法在预算内取得必需精度的能力保持未通过，并作为离线专项缺口登记；日常地图使用现有事实正常提供查询。R0/R1 总状态按 G02 所需事实判断。

### 4.3 R2：按边界家族横向连接全项目（最多 3 批）

沿用原 R2 三批：A 启动/部署，B 业务通信/后台，C 代理/插件/外部资源。每批一次扫描全部适用模块，消费已准入事实；缺少精细值流的边界明确标记依赖，不等待某个局部 getter 修完才处理其它家族。

**交付**：19 项独立参考逐项结果、全部实际边界信号处理账、129 组件入/出关系与正反向查询。逐项处理现有无跨组件入/出边标记，说明职责或应补连接。

**验收 G03–G04**：适用边界具备提供/消费/注册两端、方向、身份域和条件；请求、连接、任务、窗口和服务不因同名误连。真实上下游可分段展开；独立参考通过与全信号处理分别核查。新增模块、布局变化、改名、删除同步发现和更新。

**停止条件**：家族批次到限发布该家族的全量处理状态；未匹配位置进入统一缺口账，下一批转向下一家族。

### 4.4 R3：补数据/状态机制，形成 issue 与 diff 任务查询（最多 3 批）

按机制分三批遍历适用模块，并更新原 18 类机制矩阵：

| 批次 | 重点事实 | 任务查询要回答的问题 |
|---|---|---|
| 数据与条件 | 身份/注册/查询键，参数/返回/字段转换，SQL 与数据源，模式守卫、单位和精度 | 值从哪里来、属于谁、在哪些配置有效、被谁消费 |
| 状态与时序 | 状态读写与刷新触发、订阅/回调、任务采用/取消、资源创建/转交/清理、异常/重试 | 状态改变后谁会更新，旧对象是否仍被使用，错误如何传播 |
| 资源与任务组织 | 缓存 owner/key/失效，复制/持有，热路径频率，组件/样式/交互依赖；统一前后事实差异 | 改动影响哪些使用方，可能破坏哪些现行前提，需要什么验证 |

资源规模、频率和 UI 约束先提供源码/配置关系，实际占用、性能和布局失败由 R4 测量。跨域事实需要的精细分析沿用 R0/R1 的准入决定。

**任务查询交付**：扩展现有查询层，支持 issue 定位上下文和 diff 影响上下文。计划中的 diff 结果至少包括：

- 输入的基线/目标版本、工作树状态、构建和运行配置；变更文件与符号的前后对应。
- 变化的身份、条件、读写、触发、副作用和表示方式；每项都能定位前后来源。
- 相关提供者、消费者、共享状态/资源以及可追踪路径；函数调用边和字段流分别标记。
- 现行前提、风险候选、正负验证问题、已有测试命令及缺失测试；候选结论携带推断依据。
- 未解析、超预算、过期、截断及可续查入口。缺少前版本索引时直接列明缺失的前后比较。

这里交付的是任务查询协议及 CLI/MCP 同源实现；命令名称在实现前固定。泛化机制模型按 API/语言注册，业务模块与接口名称从源码发现。

**验收 G05 及任务查询**：18 类机制×全部适用模块逐项记账；每个通过项有实际源码、独立正负例、统一查询和变更检查。两种独立布局及模块新增/改名/删除无需改业务名称规则。任务输出能从证据追溯到受影响方和验证入口，身份/条件不匹配的对象不输出为确定影响。用 8 条开发样本演示工作流，开发成绩单列。

### 4.5 R4：运行、资源与异常验证（最多 2 批）

第一批对照 85 项冻结义务复核已有场景和可复用证据，执行缺失的边界/模式组合；第二批处理状态、异常/恢复和资源断言。场景可覆盖多项义务，逐项给出对应依据。源码采集与修改在实验副本完成。

**交付**：义务→场景/模式/断言/记录/缺口表；静态路径叠加运行事件；资源单位、采样方式、对象/进程范围；故障和恢复结果。

**验收 G06**：必需模式、边界及关键分支有实际证据和独立断言；请求/对象身份与因果明确，错版本/配置拒绝关联。内存至少区分进程 RSS、JS heap、缓存持有与可测的外部资源；静态持有关系与实际占用分别呈现。旧 P5/A5 只按原版本和场景使用。

**停止条件**：环境或数据阻塞单列，不用静态推断替代运行结果。两批结束后提交未覆盖义务和所需输入，G06 按实际结果保持通过或未通过。

### 4.6 R5：更新、预算、安装与交付收口（最多 2 批）

第一批验证新事实的失效、版本与查询，第二批验证干净安装和全模块导航，最后更新 skill。

**交付与验收 G07–G08**：

- 新增/删除/改名/改值、跨文件未改消费者、配置变化能正确更新；失败保留旧成功快照；与相同最终版本的独立重建结果一致。
- 工程/效果/精细结果缓存分别记录源码版本、配置、提供方版本、依赖和缺口；失效范围沿依赖传播。更新后旧运行记录重新检查适用性。
- 来源与配置公共元数据按引用存储，查询分页展开；只读任务查询走现有 SQLite，避免将约 4 GB 导出 JSON 整体载入。遗留必须读取整图的路径单列迁移结果。
- 干净安装能从目标仓库自动发现、建图、查全部模块和证据；CLI/MCP/skill 共用同一事实与任务查询。包内排除评测答案、原始实验数据和历史资产。

G01–G08 汇总逐门槛给出证据与失败项。局部功能通过、安装成功和 skill 包装分别记录。

## 5. 资源预算与质量约束

建图分析、图存储和 AI 查询三项独立计量，成本优化用相同版本、配置和必需事实比较。裁剪导出体积的收益记入存储/交付，不计为原生求解内存收益。

| 项目 | 执行规则/初始目标 | 收据与超限处理 |
|---|---|---|
| 日常工程索引/更新 | 初始产品目标：本地工作进程树峰值 ≤4 GiB；本轮开始测量，尚未达标 | 同时记录冷构建/增量耗时、内存和事实覆盖；超限时定位加载/重复数据，不降低模块分母 |
| 现有 SVF 诊断 | 最多一个重型分析；单次原生分析 ≤600 秒、进程树 ≤13 GiB；含导出计入批次墙钟 | 超限停止并保留阶段、原因和未产出事实；该预算只用于限时诊断 |
| 其它精细分析 | 日常查询不自动触发全程序重型求解；复用缓存，显式提交有预算的任务 | 记录分析范围、依赖和精度；局部结果无法回答时扩大待分析范围或报具体缺口 |
| 默认图查询 | 沿用 3 秒、200 节点、500 边、128 KiB 上限；超限分页/续查 | 固定查询集记录冷/热耗时、输出大小、截断和证据召回；预算到限仍返回可解释状态 |
| AI 上下文 | 先给概览及证据引用，按需展开条件、源码和运行；字节与实际 token 分别记录 | 开发阶段比较任务信息召回、代理查找开销和总 token；长度减少与效果提升分别验收 |

4 GiB 是本轮拟验证的日常索引目标，13 GiB 是既有重型诊断的停止上限，两者分别报告。绑定源码/配置的引用去重不会改变原生关系身份；points-to 只有身份验证通过后才导入。

SVF/编译分析在兼容的 Linux 环境执行；本机无现成环境时沿用已授权的研究 CI，不为本轮安装 WSL 或升级系统。本地工具、下载、临时文件、缓存和结果均放 D 盘；CI 产物下载到 D 盘并保留运行编号，公开仓库只收工具、报告和脱敏收据。

## 7. 执行顺序与 Git 交付

本轮工程投入上限为 12 个批次、18 小时主动工作；单批墙钟上限 120 分钟。前两批累计最多 3 小时主动工作后，必须确定原生采用/拒绝路线并停止扩展候选。剩余批次按 R2→R3→R4→R5 推进，独立缺口保留状态；CI 排队/运行单独记账并受单批墙钟约束。G09 的运行量由技术门槛通过后的冻结协议确定。
