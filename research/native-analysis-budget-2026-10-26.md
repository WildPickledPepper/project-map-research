# 全程序分析预算与项目图所需精度

日期：2026-10-26。证据：本项目执行收据、当前采集代码检查、上游源码/官方文档。以下成本改进均为待测方案，本轮未重新运行大规模求解，也未改变既有验收门槛。

## 1. 当前测到的成本代表什么

[C++ 资源收据](../experiments/2026-10-26-r0-r1/evidence/svf-real-resource.json)记录：411 个第一方编译单元生成输入成功，LLVM 原生 O1 处理后的输入为 163,765,192 字节；`wpa -ander -svfg` 进程在 13 GiB 上限停止，采样最高 RSS 为 13,734,240 KiB，耗时 91.256 秒，未生成完整真实后端值流结果。

这证明当前配置超预算，没有证明所需项目图的资源下限为 13 GiB，也没有测出完整运行所需峰值。原始 `analysis.log` 为空，现有收据缺少 Andersen、MemorySSA、SVFG 各阶段峰值，不能认定是哪一阶段主导。

区分三项成本：

- 求解器分析时的工作内存；
- 导出、归一化和索引占用；
- AI 每次查询接收的内容。

流式 JSON、去除重复字段、数据库索引、分页与摘要展示可改善后两项。分析完成后才裁剪原生图，不会降低前面求解时的峰值。增量缓存改善后续更新，不能独自解决首次全量分析的内存问题。

## 2. 当前流水线中可确认的问题

[C++ 重放](../experiments/2026-10-26-r0-r1/replay_svf_native.py)及[Cargo 捕获分析](../scripts/analyze_svf_captures.py)先执行 `wpa -ander -svfg -write-ander=...`，随后启动 [Python 导出](../adapters/svf_export.py)，再次在绑定中构建原生分析和 SVFG。

两次顺序求解增加总时间和工作量，也产生了 CLI/Python 节点编号跨进程对应问题。顺序运行不意味着峰值内存翻倍；当前 C++ 在第一阶段已经超预算，消除重复求解不等于已解决该峰值。

应采用与固定版本兼容的上游结果读写接口，或同进程的原生结果导出。只做结果访问/序列化适配，不实现新的指针算法；目前统一图继续不导入未验证编号的 points-to 边。

## 3. 工程关系与精细求解分层

以下是设计提案。全项目的模块、语言和机制覆盖范围保留；分析精度和执行范围按所需事实选择。

| 层次 | 需要的事实 | 计算方式与边界 |
|---|---|---|
| 全项目工程索引 | 定义/引用、类型、导入、构建与配置、注册/协议/进程两端、声明和可解析调用 | 继续复用现有 TypeScript、clangd/libclang、Jedi、rust-analyzer、CBM、CMake/Cargo 与机制适配。许多事实可直接提取；动态分派和复杂共享对象仍保留待精化问题 |
| 可组合的函数/资源效果 | 参数和返回关系、读写及副作用、身份/条件、资源和回调的输入输出 | 由适用的现成分析器或 API 模型提供结构化摘要，绑定源码/配置并保留证据。摘要需要跨函数组合；自然语言说明不能替代可组合的分析结果 |
| 精细别名/值流 | 引用/指针是否共享对象、跨函数字段影响、复杂间接目标 | 以查询和依赖为起点执行既有原生分析器，复用可靠摘要并按需扩大范围；必要时仍可触及整个程序。没有完成的必需分析列为未知，不能据此证明无影响 |
| 实际运行 | 实际实现/分支、对象和请求身份、缓存命中、内存占用、并发与清理 | 复用已有运行采集、调试/测试工具与场景；观测绑定版本和输入，不等同于静态穷举 |

从函数摘要连接全局关系，与把各个 `.cpp` 独立分析后按名字拼接不同。分析边界必须保留参数/返回、全局与共享堆对象、回调/函数指针、类型、配置和外部副作用；循环依赖由原生引擎处理，缺少摘要的外部调用不能当作无副作用。未知端口与跨边界缺口继续可查。

31 条样例要求的许多审查信息，例如功能守卫、注册键/查询键、React 刷新依赖、数据源分派与平台路径封装，本身不要求先生成整套 C++ 指针值流。但同一对象的间接写入、返回引用等问题仍需适用的别名/数据流证据。材料用于说明能力种类，不作为生产硬编码规则或新的独立验证成绩。

## 4. 上游能力核对

| 路线 | 已核对的依据 | 本项目判断 |
|---|---|---|
| SVF DDA | 上游 [DDAVFSolver::buildSVFG](https://github.com/SVF-tools/SVF/blob/master/svf/include/DDA/DDAVFSolver.h)先创建 AndersenWaveDiff，再建立 pointer-only SVFG。2026-10-26 读取默认分支，非已执行 wheel 的逐版本验证 | 按需的是后续精化，并未消除全程序前置。不能宣称换 DDA 必然降到预算内 |
| SVF 共享指向集合 | [官方文档](https://github.com/SVF-tools/SVF/wiki/Hash-Consed-Points-To-Sets)列出 `-ptd=persistent`，说明对 Andersen 内存通常相近，偶有好坏变化，流敏感分析收益更明显 | 需要核对执行版本默认值和实测，不作为有保证的内存修复 |
| SVF 对象聚类 | [官方文档](https://github.com/SVF-tools/SVF/wiki/Object-Clustering)说明针对分阶段流敏感分析，辅助阶段依赖 Andersen，并列出相关选项 | 不能把这一优化直接外推成当前 Andersen＋完整 SVFG 的解决方案 |
| 外部 API 效果模型 | [SVF extapi](https://github.com/SVF-tools/SVF/wiki/Handling-External-APIs-with-extapi.c)用模型表达返回参数、分配和复制等效果 | 适用模型可替代部分第三方内部展开；模板内联已经进入第一方 bitcode，不能简单靠排除第三方源码目录移除。没有模型的未知副作用必须保留 |
| 函数级组合分析 | [Infer 1.3.0 原理](https://fbinfer.com/docs/separation-logic-and-bi-abduction/)与[工作流](https://fbinfer.com/docs/infer-workflow/)说明分过程分析与结果组合、增量复用 | 证明该架构有现成实现。当前没有在 Insight 准入或验证它可直接导出所需通用摘要；不据此替换已用引擎或承诺成本 |
| 局部/全局数据流分开 | [CodeQL C++ 官方说明](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-cpp/)区分局部流与全局流，后者通常消耗更多时间和内存 | 支持按问题选择精度的工程方式；CodeQL 未在本项目实测，数据库构建成本也需单独计量，不承诺替换即更省 |
| 跨编译单元按需导入 | [Clang CTU 官方说明](https://clang.llvm.org/docs/analyzer/user-docs/CrossTranslationUnit.html)支持外部函数定义按需导入，并提供现成驱动 | CTU 不等于通用函数效果摘要导出，也不自动解决自定义跨进程协议。作为专门能力候选，不能当作完整项目图的现成替代 |

已下载 SVF-Python 源码为 `0befc5ba35665fdc24363a8cf573e297e21970ff`，其便利接口可以分开构建 PAG/PTA 与完整 SVFG。它与已执行 PySVF `1.0.0.50` 分发包接口存在差异；源码可见方法不代表当前 wheel 已暴露。必须先核对实际版本，不能直接把新源码行为套给已测环境。

## 5. 能收敛的处理顺序

下面是诊断/验证顺序，不是本轮已执行结果。复用现有 bitcode，不重新编译、不提高原 13 GiB 单进程预算，不同时启动多个重型求解。

1. **分离能力与阶段。** 先检查固定版本的帮助和实际 API。将“只需指向集合”和“必须有字段值流”区分；分别记录加载/建 PAG、Andersen、MemorySSA/SVFG 和导出的时间及 RSS。能在同进程分阶段时复用原生对象。
2. **去掉明确的重复。** 单次分析结果在同一身份域中导出，或用上游兼容结果文件复用；首个只需 points-to 的 CLI 阶段不应额外请求完整 SVFG。六项现有值流题仍按值流能力验证，不能用仅别名输出冒充通过。
3. **选择一个有证据的降成本试验。** 若前置 Andersen 已超预算，DDA 不是直接出口，转向经过准入的可组合/按需路线；若完整 SVFG 才主导，先验证仅需要的原生图形式及效果摘要。任何降精度配置都保留独立对象、复制后修改、借用、字段与返回关系的正负例，记录误连和漏报。
4. **核对跨模块保真。** 用不同布局和跨文件的既有独立题检查参数、返回、共享状态、回调与配置；不通过则停止该路线，不把缩小输入当成功。大程序中真正必要的全局关系仍按原验收要求补齐。
5. **设失败出口。** 同一假设只做一次有明确理由的复验；超预算或精度不合格保留证据，停止盲目重跑。重型分析可作为离线专项能力继续保留，日常项目导航不以它的全量成功作为启动前提。

当前不宣称这些处理已把 13 GiB 降至某个数值。成本结论需要同版本、同事实要求的实测；技术验收仍按[原矩阵](../plans/project-wide-acceptance.md)判定。
