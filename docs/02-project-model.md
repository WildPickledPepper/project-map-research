# 统一关系与接口模型

状态：设计假设，尚未实现。先作为不同工具输出的比较口径，不预先决定数据库或最终 schema。

## 实体与关系

| 实体 | 示例 |
|---|---|
| 模块、服务 | Timeline、通信层 |
| 文件、符号 | `getUnitFlows`、`HandleRequest` |
| 业务接口 | `module=timeline, command=unit/flows` |
| 共享数据 | 数据库表、缓存键、返回字段 |
| 场景和执行 | 项目切换场景、一次 trace、一次状态转移 |

需要区分调用、导入、继承、提供接口、消费接口、注册处理器、候选实现、读/写数据、生产/消费字段等关系。它们不能全部压成无类型的箭头。

## 如何跨语言连接

先提取两端，再按可解释规则关联：

```text
消费方：请求封装 + 模块值 + 命令值 + 参数
提供方：模块注册 + 命令常量 + handler 注册
                        ↓
           同一业务接口及其连接证据
```

语言不同不是禁止连接的原因。同语言的两个服务也需要通信模型；跨语言的 HTTP 请求则可以由方法、目标服务和路径规则关联。

接口键应考虑协议、系统/服务作用域、模块、命令或方法路径、方向和版本。只按路径或函数名全局合并会误连。

在 Insight 中，WebSocket 地址只是传输入口，`module + command` 才进一步区分业务接口。已知请求 `timeline/unit/flows` 不应扩散到所有模块的所有 handler。

## 每条关系应保留的元信息

- 所属仓库和 commit，源码路径、行号或符号定位。
- 提取器、规则或编译器索引的标识与版本。
- 证据类别：直接语法、类型解析、注册匹配、静态候选、运行观测、AI 候选。
- 适用条件、歧义候选、未解析原因、更新时间。
- 来源定位和校验片段；置信度不是正确性证明。

对于虚函数先记录接口和候选实现，并尝试提取选择条件；运行观测再记录该场景实际选中了哪一项。

## 对外查询

优先复用 MCP/CLI/JSON 等现有入口，验证以下能力：

1. 按接口查消费方、提供方和链路。
2. 按代码符号反向查业务入口和结果消费者。
3. 按变更查潜在影响，以及相关场景和验证记录。
4. 查询证据、条件、版本和覆盖缺口。

## 自动更新

结构图、协议关联、职责总结和动态证据分别标版本。以最后一次成功处理的提交为基线追赶；失败不推进成功基线；连续变更必须排队或合并，不能遇锁直接遗忘。

文件变更可能影响未修改文件中的旧关系。更新需要验证删除、重命名、改目标、常量变值、注册增删，以及全量重建等价性。

旧版本动态记录保留历史语义，不直接冒充当前版本证据。
